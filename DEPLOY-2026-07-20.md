## STAP 0 — CONTROLEER DE OMGEVING (bespaart een mislukte deploy)

Twee manieren, gebruik bij voorkeur allebei:

**A. Op de draaiende omgeving (test én productie):** log in als superadmin en open

```
GET /api/admin/config-health
```

(met de superadmin-Bearer-token). Dit draait dezelfde controles als de preflight,
maar dan op de omgeving zelf: echte runtime-env (ook in containers), live
LiteLLM-/AssemblyAI-/Recall-sleuteltests, het ECHT geconfigureerde analysemodel
(inclusief de superadmin-keuze uit de database), database-connectiviteit, en een
**bewijs** dat de JWT_SECRET van app en dashboard-backend matchen (er wordt een
echt ondertekende call naar de backend gedaan). Response: `healthy: true/false`
met per punt de oplossing. Draai dit op ELKE nieuwe omgeving — juist ook bij de
overstap naar productie.

**B. Vóór de deploy, vanaf de bron:**

```
node preflight.mjs
```

## BELANGRIJK — callbacks zijn niet meer domein-afhankelijk (2026-07-22)

De webhook-callback-URL voor AssemblyAI (transcriptie) wordt voortaan afgeleid
van de **live request-origin** (`x-forwarded-host`/`host`-headers) in plaats van
uit `APP_URL`. Gevolg: op élk domein — test, productie, tunnel — klopt de
callback automatisch, zonder configuratie. Een verkeerde of verouderde `APP_URL`
kan de pijplijn dus niet meer stilleggen (dat was de oorzaak van de mislukte
testdeploys). `APP_URL` blijft alleen in gebruik voor **e-mail-links**; wijkt hij
af van de live origin, dan logt de app een waarschuwing en meldt de healthcheck
het. Vereiste: als er een reverse proxy/load balancer voor de app staat, moet die
`x-forwarded-host` en `x-forwarded-proto` doorgeven (standaard bij vrijwel elke
hoster).

Draai dit **in de doelomgeving**, ná het zetten van de env-variabelen en ná het
herstarten van de service. Het script leest `.env`-bestanden én echte
omgevingsvariabelen (containers), print nooit secrets, en test de externe
diensten écht:

- `ASSEMBLYAI_WEBHOOK_SECRET` is **niet meer nodig** (zie rollback hieronder).
- `LITELLM_API_KEY` — wordt live tegen de gateway getest; ook of het ingestelde
  analysemodel voor díe sleutel beschikbaar is.
- `JWT_SECRET` — gezet én **identiek** in app en dashboard-backend (anders lege dashboards).
- `APP_URL` — gezet, niet localhost, en van buiten bereikbaar (anders komt de callback nooit aan).
- `ASSEMBLYAI_API_KEY`, database-URL's, dashboard-backend bereikbaar, FTP/SMTP.

Exitcode `0` = veilig, `1` = er is minstens één blokkerend probleem (met de
oplossing erbij). Alleen configuratie controleren zonder externe calls:
`node preflight.mjs --offline`.

## ROLLBACK 2026-07-22 — webhook-authenticatie verwijderd

Op verzoek van de opdrachtgever is de AssemblyAI-webhookbeveiliging teruggedraaid
naar het gedrag van de vorige werkende versie.

**Verwijderd uit `app/src/app/api/(routes)/webhooks/assemblyai/route.ts`:**
gedeelde-secret-controle (fail-closed 503/401), eigenaars-lookup (404) en de
idempotentie-check. Elk van die drie kon de callback stil afwijzen waardoor de
analyse nooit startte. **Verwijderd uit `assemblyAIService.ts`:** het meesturen
van de auth-header bij het indienen.

De code van de webhook is nu regel-voor-regel gelijk aan de versie waarin alles
werkte (alleen commentaar verschilt).

**Gevolg dat je moet kennen:** `/api/webhooks/assemblyai` is nu **niet
geauthenticeerd**. Wie de URL kent, kan een callback nabootsen en zo een analyse
laten draaien op zelf aangeleverde tekst (kosten + vervuilde dashboards).
`ASSEMBLYAI_WEBHOOK_SECRET` is niet langer nodig en mag uit de `.env`.

Wil je de beveiliging later terug, houd dan dit rekening: de secret wordt aan
AssemblyAI meegegeven op het moment van *indienen*. Zet hem dus vóórdat er
opgenomen wordt, herstart de app, en test met een **nieuwe** opname — opnames van
daarvóór blijven anders afgewezen.

## 1. Dependencies installeren (beide services)
Nieuwe dependencies deze build: `mammoth` (app + backend, docx-extractie),
`pdf-parse` (backend, plan-extractie).
```
cd app && npm install
cd ../dashboard-backend && npm install
```

## 2. Database — app (Prisma / `sales_studio`)
```
cd app && npx prisma migrate deploy
```
Relevante migraties in deze build:
- `20260630120000_total_score_to_float` — `total_score` Int→Float (mailsterren == dashboard).
- `20260703120000_add_company_terminology` — bedrijfsterminologie.
- `20260704120000_add_geen_salesgesprek` — niet-salesgesprek telt niet mee in dashboards.

## 3. Database — backend (Drizzle / `sales_dashboard`)
```
cd dashboard-backend && npm run db:push
```
Voegt toe: `transcripts.coaching_analysis` (jsonb, unificatie-bron) en
`plan_documents.structured / structured_status / structured_updated_at` (plan-upload).
> `npm start` draait `db:push` sowieso automatisch vóór de server start.

## 4. Secrets (verplicht — zie SECURITY-FIXES.md)
- `JWT_SECRET`: sterk (≥32 tekens) én **identiek** in `app/.env` en `dashboard-backend/.env`
  (anders lege dashboards / auth-fouten).
- `ASSEMBLYAI_WEBHOOK_SECRET`: **niet meer nodig in `app/.env`** (rollback 2026-07-22,
  zie boven). De gelijknamige variabele in `dashboard-backend/.env` hoort bij het
  aparte auto-import-endpoint van de backend en blijft daar wél gelden.
- `SUPERADMIN_SEED_PASSWORD`: eenmalig zetten om superadmin te bootstrappen, daarna leeghalen.
- `APP_URL`: het echte productie-domein (webhook-callback-URL wordt hieruit opgebouwd).
- Roteer alle in eerdere builds gedeelde secrets.

## 5. Modelkeuze blijft superadmin-instelbaar
De code volgt de opgeslagen model-route (superadmin-scherm); er wordt nergens een
model geforceerd. `LITELLM_MODEL`/`DASHBOARD_LLM_MODEL` in `.env` zijn alleen fallback.

## 6. Bekend / optioneel
- Backend `npm audit`: `jspdf` en `drizzle-kit` hebben breaking upgrades openstaan
  (niet geforceerd — apart plannen).
- Robuustheid: `withRetry` in `app/src/app/api/services/litellmClient.ts` racet elke
  poging tegen een 10-min timeout. Bij een (zeldzame) gateway-hik kan de analyse daardoor
  lang hangen vóór de retry het overneemt. Geen bug; optioneel de timeout verlagen
  (bijv. 120–180s) voor snellere recovery bij een flaky gateway.
